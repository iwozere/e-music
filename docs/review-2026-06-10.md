## Executive Summary

MySpotify is a thoughtfully-designed, feature-rich self-hosted music platform built for Raspberry Pi 5. The foundation — async FastAPI, dual-path streaming, intelligent LRU caching, and AI-assisted discovery — is solid. However, several issues range from a **critical performance bug** that will break at scale, to real security gaps, to maintainability risks that will compound over time. This review documents all findings with exact file references and concrete remediation steps.

**Risk ratings used:** `[CRITICAL]` `[HIGH]` `[MEDIUM]` `[LOW]` `[INFO]`

## 1. Performance

### ✅ [CRITICAL] Full table scan on every search request

**File:** `backend/app/routers/tracks.py:264`

```python
all_local_db = session.exec(select(Track)).all()
all_local = _filter_local_tracks_for_query(all_local_db, q_lower)
```

Every search request loads the **entire Track table into Python memory**, then does a Python-side substring scan. The SQL indexes on `title`, `artist`, and `album` (defined in `models.py`) are completely bypassed. At 10,000 tracks this allocates ~20 MB per request and adds ~100 ms. At 50,000 tracks it becomes the dominant latency and memory consumer.

**Fix:** Replace with a SQL `LIKE` filter pushed to the database:

```python
pattern = f"%{q_lower}%"
stmt = select(Track).where(
    or_(
        col(Track.title).ilike(pattern),
        col(Track.artist).ilike(pattern),
        col(Track.album).ilike(pattern),
    )
).offset(offset).limit(limit)
local_results = session.exec(stmt).all()
```

SQLite supports `LIKE` case-insensitively for ASCII; for full Cyrillic support, use the existing `_filter_local_tracks_for_query` as a post-filter only for the returned page (not the full table).

### ✅ [HIGH] Unbounded in-memory search cache

**File:** `backend/app/routers/tracks.py:57-58`

```python
SEARCH_CACHE: dict[str, dict[str, Any]] = {}
CACHE_TTL = 300  # 5 minutes
```

The cache grows indefinitely. Stale entries are only evicted when the same key is accessed again after TTL. A user issuing 90 unique 5-minute-spaced queries/minute (the rate limit) fills the cache with entries that are never naturally evicted. On a Pi with 1 GB RAM, this can cause OOM.

**Fix:** Use `cachetools.TTLCache` or add an LRU eviction bound:

```python
from cachetools import TTLCache
SEARCH_CACHE: TTLCache = TTLCache(maxsize=256, ttl=300)
```

### ⏳ [HIGH] Thumbnail backfill in hot request path

**File:** `backend/app/routers/tracks.py:553-566` (`get_liked_tracks`) and `tracks.py:776-780` (`get_track`)

`get_liked_tracks` iterates all liked tracks and calls `await get_track_thumbnail(t.remote_id)` serially for each YouTube track missing a thumbnail. If a user has 50 liked YouTube tracks with no cached thumbnails, this serializes 50 API calls into a single GET response. The same pattern is in `get_track`.

**Fix:** Move thumbnail backfill to a background task or a dedicated backfill worker. For the immediate request, return what's in the DB and let the client handle missing thumbnails gracefully. If backfill must happen in-request, at minimum run all fetches concurrently with `asyncio.gather`.

`ensure_admin_roles` executes `session.exec(select(User)).all()` — a full user table scan — on every application startup. Harmless today with a small user count, but worth fixing with a targeted query:

## 2. Security

### ✅ [HIGH] Refresh token hashing is not HMAC

**File:** `backend/app/auth_utils.py:94-95`

```python
def hash_refresh_token(raw: str) -> str:
    return hashlib.sha256(f"{raw}:{settings.JWT_SECRET}".encode()).hexdigest()
```

This is a **plain SHA-256**, not an HMAC. Concatenating a secret with the message before hashing (a "secret prefix" construction) is vulnerable to length-extension attacks. The standard and secure construction is `hmac.new(key, msg, digestmod)`, which the same file already uses correctly for stream URL signing on line 137.

**Fix:**

```python
def hash_refresh_token(raw: str) -> str:
    return hmac.new(
        settings.JWT_SECRET.encode(),
        raw.encode(),
        hashlib.sha256,
    ).hexdigest()
```

### [HIGH] JWT access tokens exposed in browser URL hash

**File:** `backend/app/static/main.js:108-112`

```javascript
const accessFromHash = hashParams.get('access_token') || hashParams.get('token');
```

Tokens extracted from `window.location.hash` are saved to `localStorage`. While hash fragments aren't sent to servers in HTTP requests, they do appear in:
- Browser history
- Referrer headers if the user follows a link immediately after auth
- Browser extensions that read `window.location`

The OAuth callback should POST tokens directly to the backend or use a short-lived one-time code that the frontend exchanges. At minimum, `window.history.replaceState` is called to clear the hash (line 118), which is the right mitigation, but the window of exposure is non-zero.

### [HIGH] No input validation on `limit` enables amplification

See Performance §1.5 above — an unbounded `limit` parameter is also a security concern since it can be used to DoS the server by forcing large allocations.

**File:** `backend/app/main.py:84-97`

```python
allow_methods=["*"],
allow_headers=["*"],
```

Allowing all methods and headers from the listed origins is broader than necessary. The API only uses `GET`, `POST`, `DELETE`, and `OPTIONS`. Constrain to the actual set:

```python

```

### [MEDIUM] Tokens stored in `localStorage`

**File:** `backend/app/static/main.js:111, 113`

`localStorage` is accessible to any JavaScript running on the same origin, making tokens vulnerable to XSS. For a self-hosted application this risk is lower, but if a CDN-injected or user-supplied script ever runs on the page, tokens are compromised. `HttpOnly` cookies with `SameSite=Strict` is the hardened alternative. At minimum, document this as a known trade-off.

### ✅ [MEDIUM] No minimum entropy enforcement on `JWT_SECRET`

**File:** `backend/app/config.py:18`

`JWT_SECRET: str` has no validation. The development value is `"zopa"` (4 characters), which provides approximately 0 bits of security. Add a validator:

```python
from pydantic import field_validator

@field_validator("JWT_SECRET")
@classmethod
def jwt_secret_strength(cls, v: str) -> str:
    if len(v) < 32:
        raise ValueError("JWT_SECRET must be at least 32 characters")
    return v
```

This would catch deployment mistakes immediately at startup.

### ✅ [MEDIUM] No Content-Security-Policy or security headers

**File:** `backend/app/main.py`

The application sets no security-related HTTP response headers. A CSP header, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer` should be added via middleware. FastAPI doesn't include these by default.

```python
from starlette.middleware.base import BaseHTTPMiddleware

class SecurityHeadersMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        response = await call_next(request)
        response.headers["X-Content-Type-Options"] = "nosniff"
        response.headers["X-Frame-Options"] = "DENY"
        response.headers["Referrer-Policy"] = "no-referrer"
        response.headers["Content-Security-Policy"] = (
            "default-src 'self'; script-src 'self' 'unsafe-inline' accounts.google.com; "
            "style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; "
            "connect-src 'self' https://accounts.google.com;"
        )
        return response
```

### [LOW] `stream_track` endpoint is rate-limited by IP, not by user

**File:** `backend/app/routers/tracks.py:598-600`

The `/stream/{track_id}` endpoint has no JWT requirement (only HMAC signature). The rate limiter therefore uses IP. An attacker who obtains a valid signed stream URL (e.g., via social sharing) can replay it from multiple IPs until it expires (600 s default). Consider binding stream grants tighter (shorter TTL, one-use token).

## 3. Design Patterns & Code Quality

### ✅ [HIGH] Manual database migration — no Alembic

**File:** `backend/app/db.py:34-45`

```python
SQLModel.metadata.create_all(engine)
# ...
conn.execute(text("ALTER TABLE track ADD COLUMN thumbnail TEXT"))
```

`create_all` is idempotent for new tables but cannot handle column additions, renames, or type changes. There is a single hand-rolled migration for the `thumbnail` column. As the schema grows, this pattern will cause production incidents where users run an old DB against a new codebase with missing columns.

**Fix:** Introduce Alembic:

```bash
pip install alembic
alembic init alembic
```

Set `target_metadata = SQLModel.metadata` in `alembic/env.py`. The `create_all` + manual migration can be removed once the initial migration is generated.

---

### [HIGH] `source_type` is an unconstrained string

**File:** `backend/app/models.py:44`

```python
source_type: str  # 'local', 'youtube'
```

There is no enum, Literal type, or database CHECK constraint enforcing valid values. Code throughout the codebase branches on `track.source_type == "local"` / `"youtube"`. A typo or unexpected value silently falls through to wrong behavior.

**Fix:**

```python
from typing import Literal
source_type: Literal["local", "youtube"] = "local"
```

Or use a Python `Enum` for richer validation.

### [MEDIUM] Code duplication in streaming pipeline

**File:** `backend/app/services/streamer.py:262-595`

`_stream_resolved` (~200 lines) and `_stream_legacy_subprocess` (~140 lines) share nearly identical structure: pre-buffer accumulation, stall warning, cache file write, atomic rename, success flag, cleanup in `finally`. The only difference is the data source (httpx vs. subprocess stdout).

This duplication makes every fix or improvement require touching two places. Extract the common write-and-yield loop into a `_stream_from_source(source_iter, ...)` helper.

### ✅ [MEDIUM] Deferred import inside hot endpoint

**File:** `backend/app/routers/tracks.py:683`

```python
async def ai_shuffle(...):
    from app.services.ai_shuffle import get_ai_suggestions, resolve_suggestions_to_tracks
```

A deferred import inside a frequently-called endpoint adds a dictionary lookup overhead on every call and hides the dependency from static analysis tools. Move to the top of the file.

### [MEDIUM] `PlaylistTrack` has no ORM relationship

**File:** `backend/app/models.py:70-77`

`PlaylistTrack` (the join table) defines no `Relationship` back-references to `Playlist` or `Track`. Navigating from a `Playlist` to its tracks requires a manual join query. Adding relationships would simplify the playlist router and reduce boilerplate.

### [MEDIUM] `config.py` validator is a classmethod called on instance

**File:** `backend/app/config.py:85-96`

```python
@classmethod
def strip_variables(cls, values: dict) -> dict:
    ...
def __init__(self, **values):
    super().__init__(**self.strip_variables(values))
```

`strip_variables` is decorated `@classmethod` but called as `self.strip_variables(...)` in `__init__`. This works (Python resolves it through the descriptor protocol) but is misleading. Use Pydantic's `@model_validator(mode="before")` instead for idiomatic Pydantic v2 settings:

```python
from pydantic import model_validator

@model_validator(mode="before")
@classmethod
def strip_all_strings(cls, values: dict) -> dict:
    return {k: v.strip() if isinstance(v, str) else v for k, v in values.items()}
```

### [LOW] `_stream_resolved` starts feeder thread before ffmpeg is confirmed ready

**File:** `backend/app/services/streamer.py:358-360`

The HTTP feeder thread starts immediately after `Popen`. If ffmpeg hasn't opened its stdin pipe yet (a race on slow systems), the feeder's `ff_proc.stdin.write(chunk)` can raise `BrokenPipeError` immediately. The existing `BrokenPipeError` catch handles it, but starting the feeder only after a brief read probe from ffmpeg stdout would be more robust.

---

### ✅ [LOW] `get_session` generator does not yield inside a try/finally

**File:** `backend/app/db.py:69-77`

The session is managed by a `with Session(engine) as session` context manager, which correctly closes the session. However, if an exception is raised by the route handler after the `yield`, SQLModel's `__exit__` does call `session.close()` but does **not** roll back uncommitted changes unless the exception propagates through the context manager. Under FastAPI's exception handling, `HTTPException` is caught before it reaches `get_session`. Add explicit rollback:

```python
def get_session():
    with Session(engine) as session:
        try:
            yield session
        except Exception:
            session.rollback()
            raise
```

## 4. Observability & Operations

### ✅ [HIGH] Health check has no depth

**File:** `backend/app/main.py:110-112`

```python
@app.get("/health")
async def health() -> dict:
    return {"status": "healthy"}
```

The health endpoint always returns 200 regardless of DB connectivity, disk availability, or critical background thread state. Docker's health check (`curl http://localhost:8000/health`) therefore cannot detect a crashed indexer or a locked database.

**Fix:**

```python
@app.get("/health")
async def health() -> dict:
    checks: dict = {}
    try:
        with Session(engine) as s:
            s.exec(select(func.count(Track.id))).one()
        checks["db"] = "ok"
    except Exception as exc:
        checks["db"] = f"error: {exc}"
    checks["cache_dir"] = "ok" if os.path.isdir(settings.CACHE_DIR) else "missing"
    ok = all(v == "ok" for v in checks.values())
    return JSONResponse(
        content={"status": "healthy" if ok else "degraded", "checks": checks},
        status_code=200 if ok else 503,
    )
```

### [HIGH] No structured logging / log aggregation

All logging uses the custom `setup_logger` which outputs to stdout. On a Pi running Docker, `docker logs` is the only way to view them. There is no:
- JSON log format (needed for log aggregation tools like Loki/Grafana or CloudWatch)
- Log levels controlled per module at runtime
- Correlation ID propagation beyond the `X-Request-ID` header (it's added to responses but it's unclear if it appears in log lines)

**Recommendation:** Add `structlog` or switch the formatter to `python-json-logger`:

```python
import logging
from pythonjsonlogger import jsonlogger

handler = logging.StreamHandler()
handler.setFormatter(jsonlogger.JsonFormatter("%(asctime)s %(name)s %(levelname)s %(message)s"))
```

### [MEDIUM] No Prometheus / metrics endpoint

There are no application metrics exported. For a Pi running multiple services, even lightweight metrics (request count, error rate, cache hit ratio, active downloads) would enable dashboarding and alerting. FastAPI has first-class Prometheus support via `prometheus-fastapi-instrumentator`:

```python
from prometheus_fastapi_instrumentator import Instrumentator
Instrumentator().instrument(app).expose(app)
```

Add custom counters for: YouTube cache hits, prefetch completion rate, AI shuffle latency.

### [MEDIUM] Stale `.download` files cleanup only at startup

**File:** `backend/app/main.py:60-67`

Partial `.download` files from crashed streams are cleaned up at startup but not during runtime. A stream that crashes mid-flight leaves a `.download` file until the next restart. Consider adding a periodic cleanup task (every 10 minutes) via `asyncio.create_task` in the lifespan.

### [MEDIUM] No circuit breaker for external AI calls

**Files:** `backend/app/services/ai_shuffle.py`, `backend/app/services/ai_identify.py`

Groq and Gemini API calls have a 30-second timeout but no circuit breaker. If Groq is down for an extended period, every AI shuffle request will block for 30 seconds before failing. Under load, this exhausts the thread pool.

**Fix:** Track consecutive failures and short-circuit quickly:

```python
_groq_failures = 0
_groq_open_until = 0.0

async def get_ai_suggestions(tracks):
    global _groq_failures, _groq_open_until
    if time.monotonic() < _groq_open_until:
        return []  # circuit open
    try:
        result = await _call_groq(tracks)
        _groq_failures = 0
        return result
    except Exception:
        _groq_failures += 1
        if _groq_failures >= 3:
            _groq_open_until = time.monotonic() + 60
        raise
```

### [LOW] `PlayHistory` table has no retention policy

**File:** `backend/app/models.py:78-86`

`PlayHistory` logs every single play event indefinitely. At 10 plays/day/user × 10 users = 36,500 rows/year. No deletion or archival is implemented. Add a periodic job or trigger to prune rows older than 90 days:

DELETE FROM playhistory WHERE played_at < datetime('now', '-90 days');

## 5. Testing

## 6. UI / UX

### ✅ [MEDIUM] Seek bar and volume slider are click-only (no drag)

**File:** `backend/app/static/player.js:43-66`

Both the seek bar and volume slider respond only to `click` events. Dragging — the universal interaction pattern — is not implemented. On mobile browsers and touch screens, this makes seek and volume control effectively unusable.

**Fix:** Replace click handlers with `pointerdown`/`pointermove`/`pointerup` event listeners for drag support:

```javascript
let isDragging = false;
seekBar.addEventListener('pointerdown', () => isDragging = true);
seekBar.addEventListener('pointermove', (e) => {
    if (!isDragging) return;
    // update seek position
});
seekBar.addEventListener('pointerup', () => isDragging = false);
```

### [MEDIUM] `state.searchMeta.hasMore` heuristic is unreliable

**File:** `backend/app/static/main.js:70`

```javascript
state.searchMeta.hasMore = tracks.length > 0;
```

Server-side deduplication can return fewer results than `limit` even when more exist on subsequent pages (e.g., 8 results returned for `limit=20` because 12 YouTube results deduplicated against local tracks). The client interprets this as "no more results" and stops infinite-scroll. The server should return a `has_more` or `total` field.

### [MEDIUM] No loading skeleton / placeholder UI

When the track list is loading, the UI shows only a spinner (`UI.setLoading(true)`). No skeleton cards are shown. This makes the perceived load time feel longer and causes layout shift when results arrive. CSS skeleton cards are a low-effort improvement with high perceived impact.

### [LOW] Auth modal obscures the entire page for unauthenticated users

**File:** `backend/app/static/index.html`

The auth modal is always shown to unauthenticated users, blocking access to even the public `Popular` and `Recent` views. The backend supports unauthenticated browsing (`get_optional_user`). Consider allowing unauthenticated users to browse and only showing a banner/prompt to sign in for liked tracks, playlists, and AI features.

### [LOW] No empty-state messages

When a search returns no results, the track list area becomes blank with no explanation. Add friendly empty-state messages: "No results for 'X'" for search, "No liked tracks yet" for the liked view, etc.

### [LOW] `console.log` statements left in production

**File:** `backend/app/static/main.js:2, 123, 139, etc.`

Several `console.log` statements with internal state details (`[Auth] Token detected`, `[App] Loading home tracks...`) are present in the shipped JS. These expose implementation details in browser DevTools. Strip or gate behind a `DEBUG` flag before production.

## 7. Architecture & Scalability

### [MEDIUM] No database migration strategy (Alembic)

Covered in §3 above. Worth reiterating at the architecture level: without Alembic, every schema change requires manual coordination. The current single inline migration (`thumbnail` column) will be followed by more as the schema evolves, making production upgrades fragile.

---

### ✅ [MEDIUM] SQLite write contention under concurrent users

**File:** `backend/app/db.py:12`

```python
connect_args = {"check_same_thread": False, "timeout": 30}
```

SQLite allows only one writer at a time. Under concurrent requests (playlist add + play event + AI shuffle upsert), transactions serialize and the 30-second timeout is a ceiling, not a guarantee. For >5 concurrent users, consider enabling WAL mode:

```python
from sqlalchemy import event

@event.listens_for(engine, "connect")
def set_sqlite_pragma(dbapi_conn, _):
    dbapi_conn.execute("PRAGMA journal_mode=WAL")
    dbapi_conn.execute("PRAGMA synchronous=NORMAL")
```

WAL mode allows concurrent readers and a single writer without full table locks.

---

### [MEDIUM] AI services are tightly coupled — no graceful degradation

Both Groq (AI shuffle) and Gemini (hum-to-search) are required for their respective features. An API key expiry or service outage returns a 503 with no fallback. The AI shuffle endpoint should fall back to a simpler recommendation strategy (e.g., "more tracks by the same artist" or "random liked tracks") rather than hard-failing.

---

### [LOW] Watcher and indexer threads are daemon threads without supervised restart

**File:** `backend/app/main.py:36-43`

Both background threads are `daemon=True`, which means they die silently without restarting if they crash (e.g., due to a filesystem error). The application continues serving with a stale index and no watcher. Add a supervisor loop or at minimum log a critical alert if a thread exits unexpectedly.

---

### [LOW] `yt_resolver` URL TTL of 5 hours is aggressive

**File:** `backend/app/config.py:60`

`YTDLP_RESOLVED_URL_TTL_SEC: int = 18_000` (5 hours). Googlevideo signed URLs typically expire in ~6 hours, but YouTube can invalidate them earlier (e.g., after a policy violation). The fallback-on-403 logic in `_feed_from_http` handles this, but a more conservative TTL (e.g., 3600 s) reduces the chance of serving a stale URL and hitting the fallback path.

## 8. Dependency & Supply Chain

### [MEDIUM] `yt-dlp` version is unpinned

**File:** `backend/requirements.txt`

`yt-dlp` is likely specified as `yt-dlp>=...` or without a version pin. Because yt-dlp releases frequently to keep up with YouTube changes, an unattended `pip install` can pull a breaking change. Pin to a specific version and update intentionally:

```
yt-dlp==2025.6.9
```

Add a weekly automated dependency review (Dependabot or Renovate Bot).

## 10. Strengths Worth Preserving

- **Streaming pipeline design** — dual-path (resolver + subprocess fallback) with transparent failover is elegant and production-tested.
- **Signed stream URLs** — the HMAC approach with short TTL is the right design for protecting audio endpoints without requiring JWT in every request.
- **LRU promotion on 3 plays** — the cache promotion heuristic is well-calibrated for the use case.
- **Request correlation** — `X-Request-ID` on every response is the right foundation for distributed tracing.
- **Atomic temp → final rename** — prevents partial files from being served.
- **Rate limiting per-user + per-IP** — the slowapi integration is well-structured across the API surface.
- **Cyrillic tag handling** — the garbled-tag detection and CP1251 re-decode is thoughtful and well-tested.
- **`_active_downloads` registry** — prevents duplicate downloads for the same track under concurrent requests.
